# Devin functional parity program

## Mandate and completion contract

The owner clarified on 2026-11-04 that the goal is functional parity with Devin across the product, not merely better Slack progress messages. Slack, GitHub, and Notion are mandatory integrations. A Web application is deferred, not excluded. Existing headless-only and PR-only statements describe the first implementation, not the ultimate product boundary.

**Goal:** deliver the publicly documented Devin capabilities through Touka, with executable acceptance checks and real-service evidence; build headless capabilities first and the Web surface afterward.

**Done predicate:** every capability in the versioned inventory has an acceptance scenario passing at HEAD, a live-surface verification receipt where applicable, and a resolved implementation status. An integration being registered, a tool being callable, or a green unit suite alone does not establish parity. Deferred Web, enterprise, desktop, environment, and integration capabilities remain incomplete. Proprietary models and undocumented behavior cannot be claimed equivalent without an agreed behavioral benchmark. Vendor-specific branding, command names, and billing units are not substitutes for equivalent user outcomes.

This is a multi-milestone program. Completing its first milestone does not complete this contract. The initial inventory below is a product-family discovery pass, not a completed exhaustive API or Desktop audit. Preserve unknowns rather than silently removing them from scope.

## First milestone: an agent that remains reachable

1. Persist a user-visible progress projection alongside the operation, without copying the execution state machine. Show acceptance, current activity, waiting reason, and terminal outcome. Do not publish raw reasoning, credentials, or arbitrary tool output.
2. Deliver throttled, retryable progress to the originating thread; edit one status message instead of flooding the channel. Final replies must not be overwritten by stale progress retries.
3. Answer status and read-only side questions without waiting for the active tool or changing the work. Distinguish a question from a new queued task or a steering instruction.
4. Accept steering and explicit stop/resume controls from any authorized workspace participant. A stop is not a claim that an already-completed external side effect was undone.
5. Surface repeated failure, missing credentials/tools, and approvals as explicit waiting states. Bound retries and retain work for recovery.
6. Report artifacts and verification at completion. Preserve behavior through Worker restart and provider/delivery failures.

Narrow verification commands will be attached to each implementation ticket as the owning seam is selected. Required real-service scenario: start a long-running task in Slack; another workspace member asks for status and changes direction while it runs; receive an immediate response and visible progress; stop/resume; observe exactly one coherent final outcome. Repeat through restart and a Slack rate-limit/retry fixture. The existing wildcard no-op probe proves only the actor gate, not this scenario.

## Runtime/control milestone evidence (2026-11-04)

- Pi/Chord 1.5.0 and Agents SDK 0.33.0 are pinned; daemon checksums and versioned paths match the published package. No vendor patches or deprecated-event adapters.
- `vp run verify`: 20 files / 93 tests passed, build/type checks passed, zero errors and 26 existing warnings.
- `vp test stream-frame`: real SQLite generated by Pi 1.4 preserves its transcript under 1.5 and continues idempotently. This is not proof of every in-flight checkpoint migration.
- Local workerd: HTTP continue validation/idempotency, explicit `nothing_to_answer`, removed `/retry`, and authenticated WebSocket native-view snapshot passed.
- Signed Slack controls against local workerd: duplicate requests, idle continue/steer/stop, prompt-free status, and unchanged transcript passed. During an actual local model run, status answered within five seconds; stop settled the captured operation; steering during cancellation was declined. Slack tokens were deliberately invalid: no real channel messages were sent, and vendor delivery remains unverified.
- Production remains on the previous runtime because the original operation was still active. The one-way stored-state migration and recovery boundary are documented in `docs/operations.md`. Automatic progress, full side conversations, restart/rate-limit scenarios, and the rest of the parity program are not complete.

## Decisions and sequencing

- **Decided:** functional parity is the product goal; Slack responsiveness is only its first milestone. Web is deferred, not permanently forbidden.
- **Decided:** use current primary docs as a dated baseline; track subsequent additions separately rather than continuously moving a completed acceptance target.
- **Decided:** maintain Pi Durable as the execution owner. Connectors own credentials and vendor calls; triggers own event acceptance and reply orchestration. Do not introduce a second competing agent loop.
- **Decided:** keep human-readable progress independent of a long model/tool call. Read-only side answers and steering have distinct semantics and authorization.
- **Decided:** Notion should use the existing Connector/MCP direction where sufficient. Verify actual search, page reading, and authorized writes; do not call an unconfigured endpoint 'integrated'.
- **Decided:** wider functionality is not blanket permission to silently merge, deploy, leak secrets, or give every participant every connected resource. Preserve server-side grants and make approvals explicit.
- **Throughput:** stabilize shared progress/control contracts first. Then connector-specific Slack, GitHub, and Notion work can be isolated. Core operation/outbox changes are serialized in one checkout; parallel read-only discovery is safe. Do not restart Orca orchestration without the owner's request.

## Incident evidence and current limits

The 2026-11-04 Slack report exposed two separate problems:

- An explicit one-person workspace actor policy refused other participants. Wildcard actor support was added, tests passed (88 tests in `vp run verify`), and production version `f415b13b-4f48-488d-9c97-b0e58069f513` was deployed. A signed empty-input probe from a different actor passed the gate; a different workspace remained forbidden. This did not create a synthetic task.
- The reported task was not completely stopped: its persisted transcript advanced through setup, git operations, editing and tests. Commands hit 300, 180, 400 and 120 second deadlines. Slack showed only an eyes reaction because delivery waits for a terminal result. This is poor observability and interaction, not proof that the execution engine itself deadlocked. Task completion was not established during diagnosis.

The implementation branch still needs to deliver the remaining milestones. This document is not a parity-completion claim.
